Deeptutor-HKDSE：面向 HKDSE 的 Agent-native AI 学习平台

项目概览

Deeptutor-HKDSE 基于 HKUDS DeepTutor 进行架构研究与领域化改造，将通用 AI Tutor 扩展为支持 RAG 出题、结构化批改、错题复习、口语模拟与本地模型适配的 HKDSE 备考工具链。

这个项目的重点不是宣称从零实现整个 AI Tutor 平台，而是理解一个较完整的 agent-native tutoring system，并在它的 Orchestrator、Tool/Capability、RAG knowledge base 和 LLM provider 抽象上，完成面向 HKDSE 教育场景的系统扩展。

技术栈

  • Next.js
  • Python
  • FastAPI
  • LLM Agent
  • Tool Calling
  • RAG
  • BM25
  • Structured Output
  • OpenAI-compatible API
  • MLX / Ollama / LM Studio

为什么基于 DeepTutor 扩展

从零开发一个包含文档摄取、检索增强生成、多模型 provider、流式对话、权限与 Web 前端的完整平台，并不是这个项目最有价值的部分。更合理的做法是先理解成熟开源系统的边界，再把工程精力放到 HKDSE 场景本身。

因此项目采用二次开发路线：复用 DeepTutor 的基础架构，重点补齐考试资料接入、学习工具链、结构化反馈、口语模拟和本地模型部署相关能力。

Agent-native 架构理解

项目中最核心的理解是：在 agent-native 系统里，一个能力不是普通的页面功能，而是暴露给模型的工具。

工具通常包含：

  • 给模型看的名称、描述和参数 schema
  • 后端实际执行的 FastAPI endpoint
  • 结构化的请求与响应模型
  • 必要时接入的 RAG grounding context

这种设计把“模型决定调用什么”和“代码负责可靠执行”分开，比把所有逻辑塞进一个长 prompt 更可控。

HKDSE Market 学习闭环

Market 工具链希望把单次问答变成完整学习流程：

代表模块包括：

  • PaperForge：基于知识库生成考试风格题目
  • ExamGrader：输出结构化批改结果
  • Mistake Notebook：记录错误类型与复习建议
  • FlashDeck：支持间隔复习
  • English Paper 4 Oral Practice：模拟 HKDSE 口语考试流程

RAG 与 BM25 small-corpus 问题

教育场景里的 RAG 不能只停留在“接入知识库”。项目需要处理小规模考试资料库中的检索稳定性问题，尤其是 BM25 top-k 在 small corpus 下可能出现的边界情况。

我在这个部分重点关注：

  • DSE 历年试卷与教材资料如何进入知识库
  • chunk、embedding、BM25 与 hybrid retrieval 的关系
  • 检索失败时如何避免假装已经 grounding
  • 为什么工具输出里应该保留 grounded 标记

English Paper 4 Oral Practice

English Paper 4 Oral Practice 是我主导的模块。它围绕 HKDSE 口语考试流程设计多轮模拟练习，支持多候选人讨论、考官追问、用户语音打断、流式响应清洗与 transcript-based 结构化反馈。

这个模块的价值不只是“调用一次 LLM 生成答案”，而是把真实口语考试流程拆成可交互、可追问、可反馈的 Agent 对话链路。

本地模型适配

项目参与了本地模型适配方案，支持 MLX、Ollama、LM Studio 等 OpenAI-compatible 后端。这个方向服务于教育场景里的数据隐私、本地部署和批量推理成本控制。

这部分也连接了我后续想继续补齐的模型侧能力：

  • local inference
  • quantized models
  • provider abstraction
  • grammar-constrained decoding
  • prefix cache / inference acceleration

我学到的东西

这个项目让我更清楚地理解了 Agent/RAG 项目里真正容易出问题的地方：

  • 工具 schema 和后端实现边界要清楚
  • RAG 要讲 grounding，不只是讲“接入知识库”
  • structured output 是工程契约，不是 prompt 装饰
  • 面向真实场景的 AI 产品需要闭环，而不是功能堆叠
  • 本地模型适配连接了应用工程与模型推理侧能力
